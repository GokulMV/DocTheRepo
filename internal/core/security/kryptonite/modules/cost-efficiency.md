# Cost Efficiency

## Purpose

Surface resource-inefficient code paths — N+1 queries, unbounded scans, missing caching, unbounded memory growth, chatty external calls, and fan-out/recursive cost bombs — that work fine at demo scale but drive infrastructure spend or latency out of control (or fall over) once real traffic or data volume hits.

## Applies-to (detail)

Targets any surface with a database, an API layer serving repeated requests, or outbound calls to external services: web backends, REST/GraphQL APIs, CLI tools that batch-process data, and the database/cache layer underneath, regardless of language or framework. Applies most directly where request volume or data volume can grow (listing endpoints, dashboards, report generators, background jobs, webhooks). Does not apply to a pure static frontend with no backend/database of its own — note the skip reason explicitly rather than silently matching.

## Probes

- **N+1 queries**: for every endpoint/view that returns a list of objects with related data (e.g., `GET /api/orders` returning each order's `customer` and `line_items`), enable query logging (ORM debug toolbar, `EXPLAIN ANALYZE`, or raw query count middleware) and count queries issued for N=1 vs N=20 rows returned — a query count that scales linearly with N (instead of a constant 1–2 via JOIN/`select_related`/`includes`/`with`/`preload`) is a finding.
- **Unbounded queries / missing pagination**: call every list/search endpoint with no `limit`/`page`/`per_page` parameter and check whether it returns the entire table (seed >10k rows in a test table and observe response size/time); check DB-layer queries for a missing `LIMIT` clause on any query whose result set grows with user data (not just at the API boundary — batch jobs and report exports count).
- **Missing result caps on writes**: check bulk-import or export endpoints for an enforced max batch size (e.g., "import CSV" accepting an unbounded row count in one request/transaction) that can hold a DB transaction or memory buffer open indefinitely.
- **Missing caching**: identify read-heavy, rarely-changing data (config/feature flags, category/reference lists, a user's own profile fetched on every page load, computed aggregates like "total likes") and check whether each hits the database/external API on every request versus being cached (in-process, Redis/Memcached, HTTP `Cache-Control`/ETag) with a sane TTL; measure repeated-request latency to confirm no caching layer is short-circuiting the backend call.
- **Cache correctness under load**: for any cache found, check for a stampede/thundering-herd gap — expire a hot key and fire N concurrent requests, observing whether all N regenerate the value concurrently (no lock/single-flight) versus one regenerating while others wait or serve stale.
- **Memory leaks / unbounded growth**: identify long-lived in-process state (module-level dicts/lists used as caches, event listeners registered per-request without cleanup, WebSocket/connection registries, unbounded queues) and drive repeated request/connection cycles (hundreds of iterations) while sampling process RSS — memory that climbs monotonically and never plateaus/GCs back down is a finding; check specifically for caches with no eviction policy or max-size bound.
- **Chatty external API calls**: for any code path calling a third-party API (payment processor, geocoding, LLM, email/SMS) inside a loop (once per row/item instead of batched), count the number of outbound calls for an N=1 vs N=50 item operation — linear-in-N calls to a paid-per-call or rate-limited API is a finding; also check for the same external call repeated redundantly within one request (e.g., fetching the same config from a third-party API twice in one handler).
- **Recursive / fan-out cost bombs**: locate any recursive function, tree/graph traversal, or fan-out operation (e.g., "notify all followers," "recompute all dependent rows") with no depth/breadth cap, and construct an input (deeply nested comment thread, a user with many followers/dependents) that drives call count or execution time superlinearly; check for retry logic with no backoff/cap that can multiply an outage into a request storm.
- **Egress cost bombs**: identify endpoints that stream, proxy, or re-serve large files/media (image transforms, PDF generation, "download all" archives, LLM responses with large context) and check for size/rate limits — an unauthenticated or cheaply-authenticated endpoint that lets a caller trigger unbounded outbound data transfer or repeated expensive compute (e.g., re-running an LLM call or PDF render with no per-user rate limit) is a finding.
- **Inefficient algorithms on hot paths**: profile (or read) the top request-volume endpoints and background jobs for algorithmic complexity mismatches — an O(n²) dedup/sort/search over a collection that already has an O(n log n) or O(n) library path, repeated full-collection scans inside a loop that could be a single indexed lookup or set membership check, or synchronous work on a request path that should be queued/async.
- **Missing indexes on filtered/sorted columns**: for every query with a `WHERE`, `ORDER BY`, or `JOIN` clause on a column, check the schema for a matching index; run `EXPLAIN`/`EXPLAIN ANALYZE` on the query against a realistically-sized table and flag a sequential/full-table scan where an index scan should apply.

## What "safe" looks like

List/detail endpoints issue a constant (or near-constant, bounded) number of queries regardless of how many related rows are returned — no per-row query fan-out. Every endpoint and batch job that returns or processes a growing collection enforces a maximum page/batch size, with a documented default and hard ceiling, and pushes pagination down to the database (`LIMIT`) rather than fetching-then-slicing in memory. Read-heavy, low-churn data is served from a cache with an explicit TTL and eviction policy; a cache-expiry event under concurrent load regenerates the value once (via lock/single-flight/stale-while-revalidate), not N times. Long-lived process memory plateaus under sustained repeated load rather than climbing without bound; every in-process cache has a max-size or TTL eviction policy. External API calls scale sublinearly (ideally O(1) via batching) with the number of items processed, not O(n) per-item. Recursive/fan-out operations have an explicit, enforced depth/breadth/time cap, and retries use bounded exponential backoff. Endpoints capable of triggering large data transfer or expensive compute are rate-limited per caller. Hot-path code uses the appropriate-complexity algorithm for its expected input size, and every filtered/sorted/joined column on a table above trivial size has a supporting index confirmed via query-plan inspection.

## Severity rubric

- `critical`: an unauthenticated or cheaply-reached endpoint allows unbounded resource consumption (unbounded query, unbounded recursion, unbounded egress, or unbounded paid-external-API fan-out) that can produce a runaway cloud bill or a full outage from a single crafted request.
- `high`: N+1 or missing-pagination pattern on a core, frequently-hit endpoint causing query count/latency to scale linearly with production-scale data (thousands+ of rows), materially degrading the app under real load; a memory leak that requires process restarts in production; a missing cache on a hot path causing redundant paid external-API calls at production volume.
- `medium`: N+1 or missing pagination on a lower-traffic or admin-only endpoint; a cache present but missing stampede protection; an inefficient algorithm on a hot path that degrades at scale but hasn't yet, at current data volume, caused a measurable problem.
- `low`: a missing index on a column with low cardinality or a small table where the scan cost is currently negligible; a redundant external call that is cheap/free-tier and low-volume.
- `info`: a caching opportunity on genuinely low-traffic or rarely-changing data with no measured latency/cost impact yet; a code-style algorithmic inefficiency (e.g., a list comprehension that could be a generator) with no demonstrated resource impact.

## Detection method

For N+1 and missing indexes, detection is a query-count/query-plan capture (ORM debug toolbar output, DB slow-query log, or `EXPLAIN ANALYZE`) showing query count scaling with N or a sequential scan where an index scan is expected — the literal query log is the evidence. For unbounded queries/pagination, detection is response payload size/row count and latency measured against a seeded large table, compared to the documented or reasonable page-size ceiling. For missing caching, detection is repeated-request latency and backend call count (via request logging or a network/DB call counter) showing no reduction on a cache-hit-eligible repeat request. For memory leaks, detection is process RSS sampled across N repeated request/connection cycles showing monotonic, non-plateauing growth (a simple `ps`/`/proc/<pid>/status` or language-runtime memory profiler snapshot series). For chatty external calls, detection is an outbound-call counter/mock-server hit count scaling linearly with input size instead of O(1)/O(log n). For recursive/fan-out and egress bombs, detection is wall-clock time or bytes-transferred scaling superlinearly (or unbounded) with a crafted adversarial input, captured as a before/after timing or byte-count table. Evidence for the Finding is the literal query log, timing series, memory sample series, or call-count table proving the scaling behavior.
