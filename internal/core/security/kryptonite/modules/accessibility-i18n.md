# Accessibility & Internationalization

## Purpose

Surface UI and content-handling defects that lock out users who rely on assistive technology, use a non-Latin script or right-to-left language, live in a different timezone/locale, or read the app in a language it wasn't originally built in — failures that are invisible to the original developer's setup but block or corrupt the experience for a large share of real users.

## Applies-to (detail)

Targets any surface with a rendered user interface: web frontends (server-rendered or SPA) and mobile app screens, regardless of framework. Timezone/locale-formatting and translation-completeness probes also apply to any API that returns dates, numbers, currency, or user-facing strings consumed by such a UI. Does not apply to a pure CLI with no interactive UI beyond plain stdout, or a backend-only service/library with no rendered surface and no locale-formatted user-facing output — note the skip reason explicitly rather than silently matching.

## Probes

- **Alt text**: inventory every `<img>`, icon-button, and CSS background-image used to convey information (not pure decoration) and check for a non-empty, non-filename `alt` attribute (or `aria-label` for icon-only buttons/SVGs); flag purely decorative images missing `alt=""` (forcing screen readers to announce filenames).
- **Form labels**: for every input, select, and textarea, check for a programmatically-associated label — `<label for>` matching the input `id`, or `aria-label`/`aria-labelledby` — and flag placeholder-text-as-label (placeholder disappears on input, has no accessible-name value once populated).
- **Color contrast**: measure foreground/background contrast ratio for body text (≥4.5:1), large text ≥18pt or 14pt bold (≥3:1), and non-text UI components/focus indicators (≥3:1) per WCAG 2.2 SC 1.4.3/1.4.11, using computed styles from the rendered page (via `accessibility-scan` or a contrast-checking tool); flag any text/control below threshold, including disabled-looking-but-interactive controls and placeholder text.
- **Keyboard navigation**: tab through every interactive control on each representative page/flow using only the keyboard (no mouse) and confirm every clickable element is reachable, operable with Enter/Space, and that tab order matches visual/logical order; specifically probe custom components (dropdowns, modals, date pickers, drag-and-drop, carousels) built from non-native elements (`<div onclick>`) for missing `tabindex`/keyboard handlers.
- **Focus management**: open every modal/dialog and confirm focus moves into it on open and returns to the triggering element on close; confirm a visible focus indicator (not `outline: none` with no replacement) on every focusable element; check that a route/page change in an SPA moves focus to the new content (heading or main landmark) rather than leaving focus stranded or reset to `<body>`.
- **ARIA correctness**: grep for `role`, `aria-*` attributes and flag ARIA that contradicts native semantics (`role="button"` on an `<a>` with no `href` fallback, redundant `role="button"` on an actual `<button>`), missing required states on custom widgets (`aria-expanded` on a disclosure/dropdown trigger, `aria-selected` in a tab list, `aria-checked` on custom checkboxes), and live regions (`aria-live`) missing on dynamically-injected status/error messages (toasts, form-validation errors, loading states).
- **Semantic HTML**: check for heading hierarchy that skips levels (`<h1>` to `<h3>` with no `<h2>`) or is used for visual sizing rather than structure; check for landmark regions (`<header>`, `<nav>`, `<main>`, `<footer>`) present and singular where expected; flag `<div>`/`<span>` soup used for buttons, lists, or tables where native `<button>`, `<ul>/<li>`, `<table>` would carry correct semantics for free.
- **Unicode normalization**: submit the same visual string in two different Unicode normalization forms (NFC vs NFD — e.g., "é" as a single codepoint vs. "e" + combining acute accent) to any field used for comparison, search, deduplication, or uniqueness constraints (username, email-local-part edge cases, tag search) and check whether the two forms are treated as equal or produce a duplicate/miss.
- **Emoji and astral-plane characters**: submit input containing emoji, ZWJ emoji sequences (e.g., a multi-codepoint family emoji), and characters outside the Basic Multilingual Plane (BMP) into text fields, then check storage (no truncation/corruption on save), display (renders correctly, doesn't break layout or crash the renderer), and any length-counting logic (character count using UTF-16 code units vs. actual grapheme count — flag a max-length check that mis-truncates a multi-code-unit character mid-sequence).
- **RTL layout**: switch the app/browser to an RTL locale (Arabic/Hebrew) or force `dir="rtl"` and check that layout mirrors correctly (nav, icons with directional meaning like "back"/"forward" arrows, form field order, number alignment) rather than only text direction flipping while the layout stays LTR; check bidi text (mixed RTL content with embedded LTR numbers/Latin strings) for garbled ordering.
- **Timezone / DST correctness**: create/edit a timestamp-bearing record (event, scheduled task, "created at") from a test account set to a UTC-offset timezone different from the server's, and verify display round-trips correctly; specifically test a date near a DST transition boundary (e.g., a recurring weekly event scheduled across a spring-forward/fall-back boundary) for an off-by-one-hour or wrong-day shift; check any date-only field (birthday, deadline) for timezone-shift-induced date changes (midnight UTC conversion pushing a date to the previous/next day in a non-UTC timezone).
- **Locale formatting**: render the same numeric/date/currency values under at least two locales (e.g., `en-US` vs `de-DE` vs `hi-IN`) and check that decimal/thousands separators, date order (MM/DD/YYYY vs DD.MM.YYYY), and currency symbol placement follow the active locale rather than being hardcoded to one format regardless of locale setting; check large-number grouping for locales using non-3-digit grouping (e.g., Indian lakh/crore grouping under `hi-IN`).
- **Translation completeness**: switch the app to every supported non-default locale and crawl representative pages/flows for untranslated strings (raw translation keys like `errors.generic` rendered literally, English fallback text mixed into an otherwise-translated page, or empty strings) and for text that overflows its container/truncates when translated to a longer-average-length language (German, Finnish) or breaks layout in a shorter/denser script (Chinese, Japanese).
- **Character encoding**: check HTTP response headers and HTML `<meta charset>` declare UTF-8 consistently; submit non-ASCII input (accented Latin, CJK, Arabic) through forms/file uploads and verify it round-trips through storage and back to display without mojibake (double-encoding artifacts like `Ã©` for `é`).

## What "safe" looks like

Every informative image and icon control has a non-empty accessible name; decorative images are marked so assistive tech skips them. Every form control has a programmatically-associated label independent of placeholder text. All text and meaningful UI components meet WCAG 2.2 AA contrast minimums (4.5:1 body text, 3:1 large text/UI components). Every interactive element is keyboard-reachable and operable in logical tab order, with a visible focus indicator at every stop; modals trap and return focus correctly, and SPA route changes move focus to new content. ARIA attributes match actual widget state and never contradict native element semantics; dynamic status/error content is announced via a live region. Heading hierarchy is sequential and structural, landmarks are present and singular, and native elements are used wherever native semantics fit. Unicode-equivalent input normalizes to the same comparison/storage result; emoji and non-BMP characters store, display, and count correctly with no mid-character truncation. RTL locales mirror full layout, not just text direction. Timestamps round-trip correctly across timezones including DST boundaries, with date-only fields immune to UTC-conversion date shifts. Numbers, dates, and currency render per the active locale's conventions, not a hardcoded default. Every supported locale is fully translated on representative flows with no leaked keys, no English fallback bleed, and no layout breakage from text-length variance. All content round-trips through storage/transport as UTF-8 with no mojibake.

## Severity rubric

- `critical`: a core user flow (signup, checkout, primary CTA) is entirely unreachable via keyboard or entirely unusable with a screen reader (no accessible name on the only path through the flow); a DST/timezone bug silently shifts a financial or medical-relevant date/deadline by a day; data corruption/loss on save for non-ASCII or non-BMP input (not just display) in a core flow.
- `high`: a primary interactive control (nav, form submit, modal close) fails contrast or keyboard-operability on a heavily-trafficked page; focus is lost/stranded after a modal close or route change on a core flow; a supported locale has untranslated core-flow strings (checkout, error messages) visible to real users; timezone display is wrong (not date-shifting) on a core flow.
- `medium`: secondary/less-trafficked page has a contrast, alt-text, or ARIA-state defect; RTL layout doesn't mirror on a secondary page; locale number/date formatting is hardcoded on a non-critical display; unicode normalization mismatch causes a duplicate/near-miss rather than data loss.
- `low`: heading hierarchy skips a level with no observed assistive-tech confusion in practice; translation string overflow causes minor visual truncation with content still accessible via tooltip/expansion; minor mojibake in a rarely-viewed admin/log surface.
- `info`: missing landmark region with no demonstrated navigation difficulty; decorative image missing empty `alt=""` with no content-announcement impact observed; locale formatting deviation on a locale the product doesn't yet officially support.

## Detection method

For alt text, labels, contrast, and ARIA correctness, detection is the automated rule engine's violation output (`accessibility-scan`/axe-core-class findings) grounded to a DOM selector, cross-checked by manual inspection for anything requiring judgment (meaningful vs. decorative image, ARIA state correctness under interaction). For keyboard/focus, detection is a manual keyboard-only walkthrough recording which elements were unreachable, out of order, or left focus untrapped/stranded — captured as a step-by-step repro with the DOM selector that failed. For unicode/emoji, detection is a before/after string comparison — input string vs. stored/retrieved string (byte-for-byte or codepoint-for-codepoint) revealing truncation, corruption, or normalization mismatch. For RTL, detection is a screenshot/DOM comparison between LTR and RTL render showing layout elements (icons, alignment, order) that failed to mirror. For timezone/DST, detection is the displayed/stored timestamp compared against the expected UTC-equivalent value across the DST boundary, showing an hour or day discrepancy. For locale formatting, detection is the rendered string compared against the correct locale-formatted expected string (e.g., `Intl.NumberFormat`/`Intl.DateTimeFormat` reference output) for a mismatch. For translation completeness, detection is a crawl of rendered text nodes per locale flagging raw translation-key patterns, unexpected-language text, or layout overflow (element `scrollWidth` exceeding container bounds). Evidence for the Finding is the literal DOM selector + violation, the before/after string/screenshot pair, or the expected-vs-actual formatted value.
